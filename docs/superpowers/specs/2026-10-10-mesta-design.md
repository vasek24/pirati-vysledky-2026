## 1. Goals, non-goals, success criteria
**Goal:** a separate live product at `https://mesta.dg12.cz`: one page per town council (`/brno`, `/plzen`, …) and a mobile-first index grouped by region (kraj), for the **computed** town set (§4.1): whole-municipality councils with ≥ 10 000 inhabitants where the Pirates run on their own list (type a) or in a coalition/association list (type b), plus documented borderline (7 000–9 999) and owner-forced towns. Today's computation: **78 automatic + Nové Město na Moravě (borderline, owner list)**, plus whichever of the other 8 borderline towns get a reason (computed by the generator; automatic reasons start hidden, §4.1) ⇒ **plan for ~85 (≤ 90)**. Nothing depends on the exact N (sized for N ≤ 120). The most important part: every page and card states **how the Pirates run in that town** (§6).

**Non-goals:** Senate; national/regional estimates, projections or sums (a region header shows only "Sečteno N z M měst"); precinct maps; candidate photos; Prague and its districts; statutory-city districts (městské části/obvody); any change to `praha.dg12.cz` (Worker `pirati-volby-zaloha`), `volby.dg12.cz`, `senat.dg12.cz`.

Success criteria:
- **M1 Prague runtime unchanged.** (a) `git diff --name-only <merge-base> HEAD` touches only the mesta allow-list (§3.1); (b) the Prague build made from a `git archive` export of HEAD, with the non-Prague paths deleted, is byte-identical (`dist/` and `wrangler deploy --dry-run --outdir` hash lists) to the same build of the merge-base. Checked by `scripts/check-prague-unchanged.sh`. *Why the stripping:* Tailwind 4 (`src/index.css` = `@import "tailwindcss"`, automatic source detection) scans **every non-gitignored file in the repo** — docs, JSON, scripts, `src/mesta/**` — so any committed file can change Prague's CSS and chunk hashes (verified by the review: a docs-only commit changed 7 Prague `dist/` files). That is harmless unused CSS but it is why Prague is never built or deployed from `mesta/main`.
- **M2 ČSÚ protection.** No browser calls `volby.gov.cz` (grep of the mesta build output for `appdata/kv2026`); ≤ 1 conditional fetch per ČSÚ file per feed per refresh window (≥ 20 s, ≈ 60 s typical); numbers §3.4.
- **M3 Correct inclusion and attribution.** Town set and arrangements are computed from ČSÚ data, reported in `docs/analysis/mesta-list-verification.md` and `docs/analysis/mesta-specifics.md`, checked by Codex (§6.2) and **reviewed by the owner before the domain is attached**; overrides win and must carry a reason.
- **M6 Mobile index.** At 375 px the first screen shows the search box and the "Největší města" block; first load fetches ≤ 3 shard requests (`top-1`, `top-2`, at most one region); no horizontal scroll at 320 px; tap targets ≥ 44 px.
- **M4 Correct numbers.** For 5 towns (§8) our page matches the ČSÚ results app for the same `generated` time.
- **M5 Robustness.** One failing town (data build, feed, or an empty/malformed results file inside a shard) never breaks another town, the index or Prague; existing last-good/validate/quarantine/edge/last-resort machinery reused unchanged (mesta wraps only its own shard build, §3.3).
- **M7 No leak of unreviewed attribution.** A town that is not shown (§4.4) is absent from `COUNCILS` (index, search, featured, header menu, routes) and carries `pirates:null` everywhere (API summaries, page title, Hemicycle, banner).

### 3.3 Feeds and DO keys (N + S + 2 DOs; today 79 + 16 + 2 = 97)
- **Town feed:** key = zastup, DO `volby?z=<z>`, path `/api/volby?z=<z>`, `createKvFeed({ council, conditional:true, minIntervalMs:20e3, baseUrl, headers })`; councils have `precinctFiles:false`, `map:false` (Magistrát light mode) ⇒ **2 ČSÚ files per refresh**.
- **Shard feed:** key `kraj-<id>`, path `/api/kraj?s=<id>` (edge cache key), **DO name `kraj?s=<id>-<h>`** where `h` = 8-hex FNV-1a of the sorted member zastups joined by `,` — a changed composition (re-shard after an override or a borderline call) starts a fresh DO instead of inheriting summaries of towns it no longer fetches (the overview merge copies every town missing from a candidate). `createOverviewFeed({ councils: shardTowns, concurrency: 8, waitMs: 8000, timeoutMs: 8000, … })` ⇒ ≤ 8 files, one wave, inside the 12 s deadline; refresher `kind 'overview'`. **Per-town keep-good:** mesta wraps the shard feed's `build()`: summaries with empty `parties` or `counted > total` are dropped and counted in `missing` (throw only if none remain), so the absolute structural rejects in `validate.js` (`council-parties-empty`, counted > total) cannot block the 7 other towns; `mergeOverview` then fills the dropped town from the last good snapshot.
- **Shards:** published towns grouped by `KRAJ`; region with n towns → `ceil(n/8)` near-equal shards, towns sorted by Czech name; id `<KRAJ/100>-<i>` (`21-1`). Today 16 region shards (Středočeský 10 → 2, Ústecký 12 → 2, Moravskoslezský 9 → 2, others 1). **Featured shards** `top-1`, `top-2`: the 12 most populous published towns (by population, split 6 + 6), same feed type; these towns are also in their region shard (12 extra ČSÚ GETs per cycle, accepted); the client takes the summary with the newer `parseCsuTime(generated)` (`pickSummary`) and keeps only a shard's **current** members (`SHARDS[id].zastups`).
- **First class (cron warm-up):** all region shards + `top-1`, `top-2` + the 12 most populous published towns' own feeds (30 keys today); `runWarmup(keys, callFeed, { concurrency: 8, timeoutMs: 15000 })`. Other towns on demand with the existing bounded wait.

### 3.4 Index data path (decision: region shards + featured shards, lazy polling) and load
| Option | Edge req / index viewer / min | ČSÚ GET/min for the index | New code |
|---|---|---|---|
| per-town summaries | N (≈ 85) | N | small |
| **shards ≤ 8, polled only while visible (chosen)** | **typ. 3–4, max S + 2 (18)** | **N + 12** | none: `createOverviewFeed` + overview refresher |
| one aggregate DO over shard DOs | 1 | N | DO→DO fan-in, new merge path, one failure domain |
- Each shard is a `useLiveResults` source `{ key:'kraj.<id>', url:'/api/kraj?s=<id>', version: OVERVIEW_VERSION, arrivals:false }` scheduled by `nextRefreshAt` + per-tab offset 0–25 s. **A region shard is mounted (fetched and polled) only while its section is expanded and on screen** (IntersectionObserver); collapsing or scrolling away unmounts the hook. Featured shards are always mounted.
- **Edge, 10 000 viewers:** typical (featured + 1–2 regions) ≈ 3.5 × 10 000 = 35 000 req/min ≈ 600 req/s; worst (everyone expands everything) 18 × 10 000 = 180 000 req/min ≈ 3 000 req/s, almost all Cache-API HITs; Worker invocations ≈ 8–43 M in 4 h (Paid, ≤ ≈ $13). Town viewers: 1 req/min.
- **DO:** ≤ 1 request per key per colo per edge TTL (1–5 s counting) ⇒ ≤ ~20 req/s per DO in the worst second, typically < 4.
- **ČSÚ (conditional GET, mostly 304), counting phase:** region shards N + featured 12 + warm town feeds 12 × 2 + on-demand town feeds ≤ (N − 12) × 2 ⇒ **≤ 3N + 12 ≈ 270 GET/min ≈ 4.5/s at N = 85**; ceiling at the 20 s floor everywhere ≈ 810/min. Independent of viewer count. No precinct files.

### 3.5 Partial builds and freshness
Shard keeps a failed or malformed town's last good summary (wrapper + overview merge); a town without data shows "zatím bez dat". Each town row shows **its own** ČSÚ time (`parseCsuTime(generated)` HH:MM) and progress; no headline sums. Region header "Sečteno N z M měst" (towns with `counted ≥ total > 0`, counting only shown towns). Shard `stale:true` ⇒ orange line on that region only.

## 4. Data: generator, inclusion, overrides, data build
### 4.1 Inclusion rule (generator `inclusion` field)
Candidates = every `kvrzcoco` council with `TYPZASTUP 1`, `DRUHZASTUP ≠ 4`, plus the owner-list names. Per candidate: population `POCOBYV`, type a/b/c/d (§6), owner-list membership, automatic borderline reasons. Then:
- `auto`: population ≥ 10 000 and type a/b.
- `borderline-included`: 7 000–9 999 (or `population-band-differs`) and type a/b and ≥ 1 reason: `owner-list`; `okres-seat` (town name = `cnumnuts` NAZEVNUTS of its OKRES); `senate-seat-2026` (town name = a 2026 Senate constituency name); `pirates-2022` (a 2022 list with 720 in SLOZENI had ≥ 10 % or ≥ 1 seat: reason text "Piráti 2022: 11,7 %, 2 mand."); or a manual `borderlineReason` in overrides (Senate-constituency seat, home of a Pirate-backed candidate, high-profile coalition — free text, required).
- Confidence of borderline towns: included through `owner-list` or a manual `borderlineReason` ⇒ normal confidence (Nové Město na Moravě); included **only** through automatic reasons (`okres-seat`, `senate-seat-2026`, `pirates-2022`) ⇒ `confidence: 'low'` + flag `borderline-auto` (hidden until the owner reviews). All reasons are computed by the generator and printed in the reports.
- `borderline-excluded`: 7 000–9 999 type a/b without any reason ("borderline, no reason").
- `forced`: overrides `include: true` with `reason` (any population/type; c/d towns then render their c/d banner).
- `excluded`: everything else, with reason (`population <N>`, `type c`, `type d`, `override include:false: <reason>`).
Published set = `auto ∪ borderline-included ∪ forced`. Owner-list names that do not match exactly one council are reported as `unmatched`/`ambiguous` and stop the generator (exit 1). Duplicate published slugs get `-<okres-name slug>` appended + flag `slug-disambiguated`.

## 6. Pirate attribution rules
1. Pirate lists = town's kvros rows with 720 in `SLOZENI`. One with `VSTRANA 720` ⇒ **a**; otherwise ⇒ **b**, `kind` from cvs TYPVS (K coalition, D association), `partners` = SLOZENI codes ∉ {720, 80} named by cns `ZKRATKAN8`, `independents` = 80 ∈ SLOZENI, name `NAZEVCELK`, short `ZKRATKAO30`.
2. `members` = kvrk `PLATNOST A`, `PSTRANA 720` on the Pirate list. `others` = same filter on lists without 720 (`nominatedBy` = cns short of NSTRANA). No Pirate list: `others` non-empty ⇒ **c**, else **d**.
3. > 1 Pirate list ⇒ lowest list number, flag `multiple-pirate-lists`.
4. "Pirate" = PSTRANA 720 or composition 720; supporters without membership are not detectable (owner adds via overrides; the table header says so).
5. Flags: `disambiguated-by-druh`, `dash-normalized`, `slug-disambiguated`, `kraj-differs-from-owner-list`, `named-cps-but-association`, `no-members-on-pirate-list`, `population-band-differs`, `borderline-auto`, `jmsez-mismatch`, `unknown-partner-code`, `multiple-pirate-lists`, `also-on-other-lists`. **Low confidence (generator)** = `multiple-pirate-lists`, `jmsez-mismatch`, `unknown-partner-code`, `population-band-differs`, `borderline-auto`; **override** `confidence:'low'` (Codex findings) is a separate, stronger low (§4.4 shown rule).

## 7. Robustness
Town feed failure: town DO keeps last good (stale + backoff); its index row still comes from the shard. Malformed town inside a shard: dropped by the mesta build wrapper and filled from last good (§3.3). Shard failure: other shards unaffected; Worker last-resort copy, 503 JSON only without a copy. Data-build failure: release blocked while a published town lacks `public-mesta/data/<slug>/lists.json` (fix, or override `include:false` with reason). Mesta shares no DO/KV/cron with Prague.
